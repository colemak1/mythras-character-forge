# Mythras Forge: Core rule scope and verification register

Source: user-uploaded `pdfcoffee.com_mythras-2e-2-pdf-free(20261021-212124).pdf`, Mythras Core Rulebook. Printed contents pp. 2–3 visually inspected; individual rules require verification on their own pages before an item is marked verified. This is a **working scope**, not a claim that every rule in each range has been enumerated. Page ranges identify where an audit starts and may cross adjacent pages.

## What we mean by complete

The target is a Core-accurate character and table companion: a supported mechanic must match Core for its stated cases, preserve character data and give correct results through the relevant player and GM workflows. A GM judgement can remain manual if the app clearly represents that decision and does not claim to calculate it. A rule is not verified just because the UI has a control or a test passes.

The target includes Core character creation, characteristics and skills, equipment, advancement, combat, wounds, recovery, magic and campaign configuration. Core optional rules must be identified as optional and controlled by the appropriate campaign setting where implemented. Existing deliberate Sit'ota house rules stay distinct from Core and are not removed without the user's direction. Supplement mechanics, including Classic Fantasy, Mythic Babylon and M-Space, are deferred until Core is complete; recording a book selection does not mean its rules work.

The book also includes guidance, tables, creature statistics and setting-dependent decisions that are not necessarily automatic character-sheet calculations. The provisional targets below label these **GM-assisted**, **reference**, or **scope decision needed**. They are not silently excluded from Core. Before treating any as outside the final product, confirm the intended workflow; absence of a feature is not itself a reason to exclude a rule.

## How to use this register

- **Target:** `automate` means correct calculations, constraints and outcomes where appropriate; `GM-assisted` means explicitly record or support choices and outcomes without automating the GM's judgement; `reference` means accurate findable guidance or manual use of the book, subject to publishing rights; `decision` means the required product behavior has not been decided. These are proposed targets, not verified descriptions of current behavior.
- **Source review:** `not assessed`, `partial`, `verified`, `discrepancy`, or `interpretation` with source pages and scenario evidence. A group may be partial even if some subrules pass.
- **Implementation and live test:** independently `not assessed`, `partial`, `pass`, `fail`, or `not applicable`, with commit/version, reproducible inputs, expected and actual results, and date. Mocked tests are not live tests. A single example does not verify an entire group.
- Subdivide a row before calling it verified if it contains more than one independently testable rule or any unreviewed exceptions. Preserve the original ID when splitting, e.g. CH-01a. Track both a pass and a failure in the evidence log rather than concealing mixed results.
- Maintain separate measures: source-reviewed cases / enumerated cases, passing implemented cases / applicable implemented cases, and passing live workflows / enumerated live workflows. List unsupported and undecided items separately. **Do not combine them into a book-wide percentage** until inventory completeness, scope, weighting and the denominator have been explicitly established. Manual rules count only when their stated manual behavior is verified; they do not count as automated.
- Individual spell descriptions, effects, creatures and equipment entries each require their own auditable children. A group row is a placeholder and cannot be counted as one verified rule.

## Verification sequence

1. Expand CH/CU/CR into individual cases using the printed pages and current app code. Record a case even when behavior is unsupported or GM-managed; add reproducible tests for meaningful boundaries and data preservation.
2. Expand skills, equipment and the game system. Resolve or explicitly document interpretations, including combined fatigue/encumbrance, before marking them verified.
3. Expand combat into actions, each effect and interactions; test wound and recovery workflows end to end.
4. Expand each magic tradition, ability and relevant interaction. Confirm copyright/licensing before publishing Core text.
5. Exercise signed-in GM/player workflows, security boundaries, save/reopen, campaign options, imports and migrations against the exact deployed revision. Repeat only where fixes or unresolved concerns warrant it.

For every audit batch record the source pages, code revision, tests, live result, known gaps, and a short changelog. Update this register in the same change as the evidence. Any estimate must be explicitly labelled as a rough judgement until the detailed inventory is complete.
